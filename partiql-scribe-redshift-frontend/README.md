# PartiQL Scribe Redshift front end

Converts an Amazon Redshift query to a PartiQL AST. The caller plans the AST with the PartiQL planner against its own
session and compiles the plan with `Scribe.compile` and any target (`PartiQLTarget`, `RedshiftTarget`, `SparkTarget`,
`TrinoTarget`, `DuckDBTarget`). The front end needs no session and no planner, and nothing Redshift-specific reaches the
targets.

**Bring your own grammar of Redshift.** The module does not ship one: it converts the parse tree, and you supply the
ANTLR grammar that produces it, as the parser your build generates from it, `RedshiftGrammar`. See "Supplying the
grammar" below.

```kotlin
val context = ScribeContext.standard()
val frontend = RedshiftFrontend(context, RedshiftGrammar.of(RedshiftParser::class.java))   // your generated parser
val tables = frontend.tables(sql)                                   // the tables the query reads, to build the Session
val ast = frontend.toAst(sql)                                       // the PartiQL AST
val plan = PartiQLPlanner.standard().plan(ast, session).plan
val output = Scribe(context).compile(plan, session, PartiQLTarget).output.value
```

A problem found while converting is reported to the context's problem listener as a `ScribeProblem` with the `LINE`
and `COLUMN` of its position in the Redshift text, and the one that stops the conversion is thrown as
`ScribeException`. It is an `UNSUPPORTED_OPERATION` whose `RedshiftFrontend.KIND` property says which:
`KIND_SYNTAX` (the text is not in the grammar), `KIND_UNSUPPORTED` (a construct that parses but has no conversion yet),
or `KIND_INVALID` (a form Redshift rejects, such as an ordinal out of range); the message starts with the kind in words. A rewrite that changes the shape of the query (a
`DISTINCT` query with `LIMIT` becomes a subquery) is reported as `TRANSLATION_INFO`. An unknown name, or an operation
PartiQL does not define on the operand types, is found by the planner, not by the front end.

`tables(sql)` lists the tables the query reads, from the same conversion as `toAst`, so a common table expression counts
as a table exactly where the AST reads it as one.

### Supplying the grammar

You bring your own grammar of Redshift; the module ships without a parser. The front end is compiled against the
classes ANTLR generates from a grammar named `Redshift`, so the grammar plugs in as that generated parser: your build
generates it, and you hand it to `RedshiftFrontend` as a `RedshiftGrammar`. Your grammar must be named `Redshift`, and
its rule, label, and token names must be the ones the front end reads (the "Grammar" section below says what it
parses).

In a Gradle project that depends on the module, with your grammar at `src/main/antlr/Redshift.g4`:

```kotlin
plugins { antlr }

dependencies {
    antlr("org.antlr:antlr4:4.10.1")                        // RedshiftFrontend.ANTLR_VERSION
    implementation("org.antlr:antlr4-runtime:4.10.1")
    implementation("org.partiql:partiql-scribe-redshift-frontend:<version>")
}

val parserPackage = "org.partiql.scribe.frontend.redshift.antlr"   // RedshiftFrontend.PARSER_PACKAGE
tasks.generateGrammarSource {
    arguments = listOf("-visitor", "-no-listener", "-package", parserPackage)
    outputDirectory = layout.buildDirectory.dir("generated-src/antlr/main/${parserPackage.replace('.', '/')}").get().asFile
}
tasks.compileKotlin { dependsOn(tasks.generateGrammarSource) }
```

Then `RedshiftGrammar.of(RedshiftParser::class.java)` names the parser (the import
`org.partiql.scribe.frontend.redshift.antlr.RedshiftParser` does not compile until your build has generated it), or
`RedshiftFrontend(context)` finds it on the class path, through the class loader that defined the front end, which is
the loader the front end's own references to the parser resolve against; in an application that isolates class
loaders per jar, the parser must be visible to the module's. The ANTLR tool and runtime versions must be the same,
4.10.1: the runtime refuses a parser generated by another version at the first parse, and `RedshiftGrammar` checks the
runtime's version up front. A missing parser, another class, or another runtime version is an `IllegalStateException`
from `RedshiftGrammar` or the constructor, naming this contract.

Building the module itself from source, `src/main/antlr/Redshift.g4` is a blank placeholder for your grammar: put it
there and build, and the parser is generated into the module and packaged in its jar. While the placeholder is blank,
the module's own build compiles against, and its tests run with, the parser of an example grammar in the test tree,
generated under the name `Redshift` through a stub the build writes; the jar leaves it out. With a grammar in the
placeholder, the tests run against that grammar instead (the grammar fixtures describe the example).

One rewrite depends on the caller's catalog: `POWER`, `POW`, and `^` become a call of `pow`, which PartiQL's built-in
functions do not define. Plan against a catalog that defines it (`Pow.overloads()` of
`org.partiql:partiql-function-extensions`, which `partiql-scribe-function-extensions` compiles for each target), or
these queries fail to plan with `FUNCTION_NOT_FOUND`.

A query that nests deeper than `RedshiftFrontend.MAX_NESTING` (200) is refused: parentheses or `CASE` expressions open
at once, prefix operators (`NOT`, `-`) in a row, and levels of the AST, where each subquery, `CASE`, join, `UNION`, and
each operator of a chain is a level (`a AND b AND c` is two deep). The bound on the text keeps the parser's recursion
bounded, and the bound on the AST keeps the planner's and the targets' recursion bounded. The parser runs with SLL
prediction first and full LL only when SLL finds an error, which keeps its decision cache small.

## Grammar

The grammar is an ANTLR 4 grammar of the subset of the Redshift *query* language that the front end
translates: the constructs with a PartiQL counterpart that Scribe's targets accept, directly or by an exact rewrite.
What parses either translates or is refused at its position; everything else is a syntax error with a line and column. It is case-insensitive and
follows PostgreSQL operator precedence, from which Redshift derives.

What parses:

- One `SELECT` query, with an optional trailing `;`. `DISTINCT`, `ALL`, `TOP n`, `* EXCLUDE (...)`, `WITH`,
  `FROM` (required) with tables, subqueries, and `[INNER | LEFT | RIGHT | FULL [OUTER]] JOIN ... ON`, `CROSS JOIN`
  and comma joins, `WHERE`, `GROUP BY` (expressions and ordinals), `HAVING`, `UNION [ALL | DISTINCT]`,
  `ORDER BY ... [ASC | DESC] [NULLS FIRST | LAST]`, `LIMIT n | ALL`, `OFFSET n`, and subqueries in every clause.
- Expressions: `+ - * /`, unary sign, `^`, `&`, `||`, datetime arithmetic (`d + 1`, `d1 - d2`,
  `ts + INTERVAL '1 day'`), `CASE`, `CAST`, `::`, `CONVERT`, scalar subqueries, and names of up to three parts.
- Conditions: `= <> != < > <= >=`, `AND OR NOT`, `IS [NOT] TRUE | FALSE | UNKNOWN`, `[NOT] LIKE | ILIKE ... [ESCAPE]`,
  `[NOT] BETWEEN`, `IS [NOT] NULL`, `ISNULL`, `NOTNULL`, `[NOT] IN (list | subquery)`.
- Literals: integer, decimal, string (with `''` and backslash escapes), `DATE '...'`, `TIMESTAMP '...'`,
  `INTERVAL '...'` (no qualifier), `TRUE`, `FALSE`, `NULL`.
- Types: `SMALLINT`, `INTEGER`, `BIGINT`, `DECIMAL(p, s)`, `REAL`, `DOUBLE PRECISION`, `CHAR(n)`, `VARCHAR(n)`,
  `DATE`, `TIMESTAMP`, `BOOLEAN`, each with its Redshift aliases.
- Functions, each with its own argument form: `AVG`, `COUNT`, `COUNT(*)`, `MAX`, `MIN`, `SUM` (with `DISTINCT`);
  `DECODE`, `GREATEST`, `LEAST`, `NVL`, `COALESCE`, `NVL2`, `NULLIF`; `CAST`, `CONVERT`; `CURRENT_DATE`, `DATEADD`,
  `DATEDIFF`, `GETDATE()`, `SYSDATE`, `EXTRACT(EPOCH FROM ...)`; `POWER`, `POW`; `CONCAT`, `LOWER`, `UPPER`. Any other
  function call is a syntax error at its opening parenthesis.

The generated parser is in the package `org.partiql.scribe.frontend.redshift.antlr`; it is not part of the module's
API, and the jar packages it only when a grammar is in the placeholder (see "Supplying the grammar" above).

## Translation

Each rule rewrites a form of the Redshift query into a form of PartiQL; the planner then resolves names and types. A
query the planner cannot type (an operation Redshift defines on types PartiQL does not, for example `c || b` with `b` an
integer column) fails at the planner with its reason. The rewrites:

| Redshift | PartiQL |
|---|---|
| `TOP n` | `LIMIT n` |
| `LIMIT ALL` | no limit |
| `DISTINCT` with `LIMIT` or `OFFSET` | a `DISTINCT` subquery with `ORDER BY`, `LIMIT`, and `OFFSET` outside, because PartiQL evaluates `DISTINCT` after `LIMIT`; items that share an output name get their own names inside (`$1`) and the shared name back outside |
| `GROUP BY 1`, `ORDER BY 1` | the select-list expression; an ordinal that points at `*` is refused, as the columns behind `*` are known only after planning |
| `ORDER BY name` | the select item of that output name (its alias, or the column it selects), when the key is only the name (an output name wins in `ORDER BY`); a name inside an `ORDER BY` expression stays an input column; a name that several items have is ambiguous and refused unless they are the same expression (`x.b` and `b` over one FROM item are) |
| `ORDER BY` under `DISTINCT` with `LIMIT` | the key is matched to the select item it names or repeats, and the outer query sorts by that item's column; under `*` it must be a column of the relation behind the `*` |
| `* EXCLUDE (c)` | `EXCLUDE t.c`, qualified with the single FROM item or the relation the query names; a qualifier the query writes must be a FROM item, and the relation behind a `t.*` |
| `x::t`, `CONVERT(t, x)` | `CAST(x AS t)`; `VARCHAR` and `TEXT` are `VARCHAR(256)`, `CHAR` is `CHAR(1)`, `BPCHAR` is `CHAR(256)`, `DECIMAL` is `DECIMAL(18, 0)`, `VARCHAR(MAX)` is `STRING`, `CHAR(MAX)` is `CHAR(4096)`; a length or precision outside Redshift's range is refused |
| `LIKE` | a literal pattern is rewritten to the form PartiQL takes: Redshift escapes with `\` by default, takes an escaped character of any kind literally, and takes `ESCAPE ''` as no escape; PartiQL takes an escape only before `%`, `_`, and the escape character, so `'a\\b'` is `'ab'` and `'%start\\_%'` is `'%start\_%' ESCAPE '\'`. A pattern that is not a literal keeps Redshift's escape character |
| `ILIKE` | `LOWER(a) LIKE b` with a literal pattern lowered in that form, which cannot turn a letter into the escape character; `LOWER(a) LIKE LOWER(b)` for another pattern, whose escape character must not be a letter |
| `ISNULL`, `NOTNULL`, `!=` | `IS NULL`, `IS NOT NULL`, `<>` |
| `ORDER BY x` | `ORDER BY x ASC NULLS LAST` (Redshift's default order, written explicitly) |
| `t1, t2` | `t1 CROSS JOIN t2` |
| `WITH` | kept as `WITH`; a common table expression is referenced as a local variable, so a table of the same name does not capture it |

The conditional functions, each rewritten to the PartiQL expression with the same value; the planner types the result
as it types any expression:

| Redshift | PartiQL |
|---|---|
| `NVL(e1, ..., en)`, `COALESCE(e1, ..., en)` | `COALESCE(e1, ..., en)` |
| `NULLIF(a, b)` | `NULLIF(a, b)` |
| `NVL2(e, a, b)` | `CASE WHEN e IS NOT NULL THEN a ELSE b END` |
| `DECODE(e, s1, r1, ..., sk, rk [, d])` | `CASE WHEN m1 THEN r1 ... WHEN mk THEN rk ELSE d END`, where the match `mi` is `e IS NULL` when `si` is the NULL literal (`si IS NULL` when `e` is), `e = si` when either is another literal, and `e = si OR (e IS NULL AND si IS NULL)` when both may be NULL, since a NULL search value matches a NULL `e` |
| `GREATEST(v1, ..., vn)`, `LEAST(v1, ..., vn)` | NULL literals left out, then `CASE WHEN c1 THEN v1 ... WHEN c(n-1) THEN v(n-1) ELSE vn END`, where `ci` is the conjunction over `j > i` of `vi >= COALESCE(vj, vi)` (`<=` for `LEAST`): a NULL `vi` fails its branch, a NULL `vj` does not stop `vi`; one argument left is `COALESCE(v, NULL)` (so the item keeps its own name), all NULL is NULL |

The string and math functions, and the operators that go with them:

| Redshift | PartiQL |
|---|---|
| `UPPER(s)`, `LOWER(s)` | `UPPER(s)`, `LOWER(s)`: the result has the argument's type, and a `CHAR(n)` keeps its padding, in both languages. The case mapping is the target engine's: `UPPER('straße')` is `STRASSE` on an engine with full Unicode case mapping, and `STRAßE` in Redshift |
| `CONCAT(a, b)`, `a \|\| b` | `a \|\| b`, NULL when either side is NULL in both languages. Redshift converts an operand that is not a character string to `VARCHAR`; the conversion depends on the operand's type, which the front end does not see, except for a numeric literal, which is written as the string it converts to: `c \|\| 007` is `c \|\| '7'`, `CONCAT('v', 1.50)` is `'v' \|\| '1.50'`, `c \|\| -1` is `c \|\| '-1'`. Another non-string operand (a column, `NVL(seats, 0)`) is left to the planner, which reports the type mismatch. A subquery is allowed as an argument of `CONCAT`, since it becomes an operand of `\|\|`, which prints with its parentheses |
| `a & b` | `a & b`, PartiQL's bitwise AND. Redshift defines `&` on integers only; a decimal literal operand is refused as invalid, and a decimal column (which the front end cannot see) is cast to `BIGINT` by the planner, which rounds |
| `POWER(a, b)`, `POW(a, b)`, `a ^ b` | the call `pow(CAST(a AS DOUBLE PRECISION), CAST(b AS DOUBLE PRECISION))`: Redshift's `POWER` converts its arguments to `DOUBLE PRECISION` and returns one, and the casts make a catalog with one `pow` overload per numeric type (`Pow.overloads()` of `partiql-function-extensions`) resolve the `DOUBLE PRECISION` one, not the integer one with `1.5` cast down. The name is `pow`, that of the extension, where SQL names the function `POWER`; PartiQL has no built-in of either name, and the planner reports `FUNCTION_NOT_FOUND` against a catalog without `pow`. `^` is left-associative, binds tighter than `*` and looser than a sign, as in Redshift: `2 ^ 3 ^ 2` is `pow(pow(2, 3), 2)` and `-2 ^ 2` is `pow(-2, 2)`; a subquery operand of `^` is refused like a subquery argument |

A wrong number of arguments (`NULLIF(a)`, `NVL2(e, a)`, `DECODE(e, s)`, `UPPER(a, b)`, `CONCAT(a)`, `POWER(a)`) and
`&` with a decimal literal operand are refused as invalid.

`DECODE`, `GREATEST`, and `LEAST` repeat their arguments in the rewrite, and a call nested in a repeated position repeats
the repetition, so the size of the AST of a statement is bounded: at most 100,000 nodes as the planner walks them, where
a shared node counts at each use, a string literal weighs one node per 16 characters, and a reference to a common table
expression weighs the body it stands for (the planner inlines it there; the `WITH` clause itself counts nothing). The
bound is checked as each repeating rewrite is built, on the running total of their results (a rewrite nested in another
counts once, as part of the outer one), so that no oversized tree is built, and then on the finished statement, which
also covers an alias that `GROUP BY` or `ORDER BY` repeats and a common table expression referenced several times. The
refusal names the function when its rewrite crosses the bound, and the query when the finished statement does. A
statement that repeats nothing is not measured: its AST is the size of its text, and the depth bound keeps it walkable
(`IN` over 50,000 literals, 30,000 select items, and a 2 MB string literal convert). Measured edges: a `GREATEST` of
129 columns converts and one of 130 is refused; `DECODE` nested 12 deep in the expression with column search values
converts and 13 is refused; `GREATEST(x, b, 1)` nested 6 deep converts and 7 is refused; two `GREATEST`s of 120 columns
in one statement are refused together; `GREATEST` of 91 columns with its alias in `ORDER BY` converts and 92 is refused;
a common table expression of `GREATEST` over 120 columns converts referenced once and is refused referenced twice.

A Redshift identifier is at most 127 bytes; a longer one is refused as invalid, before the planner sees it.

Not converted yet, and refused with `UNSUPPORTED_OPERATION` at their position: the datetime functions (`DATEADD`,
`DATEDIFF`, `GETDATE`, `SYSDATE`, `CURRENT_DATE`, `EXTRACT(EPOCH ...)`), the `INTERVAL` literal and datetime arithmetic, a `DATE` or
`TIMESTAMP` literal in a form other than `YYYY-MM-DD` and `YYYY-MM-DD HH:MM:SS[.ffffff]`, a backslash escape in a string
literal other than `\\`, `\'`, `\b`, `\f`, `\n`, `\r`, `\t`, a numeric literal of more than 38 digits, a column list
on a derived table or a common table expression, `*` with other select items, `EXCLUDE` with select items other than `*`
or of an unqualified column with several FROM items, a subquery inside an `IN` list or as a function argument, which an
operand of `^` becomes (the PartiQL printer writes it there without its parentheses; a subquery inside an argument
expression, `GREATEST(b, (SELECT ...) + 1)`, is allowed, and repeated like any other argument), a comparison or a boolean connective as the operand of
`IS [NOT] NULL`, `ISNULL`, `NOTNULL`, or `IS [NOT] TRUE | FALSE | UNKNOWN`, written by the user or by the rewrite of
`NVL2` and of a `DECODE` match on NULL (the printers write `a AND b IS NULL`, which reads as `a AND (b IS NULL)`;
`DECODE(a AND b, TRUE, ...)` is fine, its match is `=`), `ORDER BY`, `LIMIT`, or `OFFSET` on
a parenthesized query that has its own, an `ORDER BY` or `GROUP BY` ordinal that points at `*` or follows a set
operation, `ILIKE` with an escape character that is not a literal, or a letter when the pattern is not a literal, an
`ORDER BY` name that several select items have when they may be different columns (`b` and `y.b` over several FROM
items), and under `DISTINCT` with `LIMIT` an `ORDER BY` key that is not a select item, `*` over several FROM items,
`t.*` next to other items (a column name may repeat there, which the outer query cannot tell apart without the schema),
and a qualified key of another relation than the `*`. A select-list alias used in `WHERE`, `GROUP BY`, `HAVING`, or a
later select item (a lateral column alias) is left as a name: Redshift reads it as the alias only when no FROM column
has the name, which needs the schema and is a later change; for now the planner reports it as unknown.

A limit of the planner, not of the front end: a query that groups by an expression and orders by the same expression,
by its alias, or by its ordinal (`SELECT UPPER(c) AS u, COUNT(*) FROM t GROUP BY UPPER(c) ORDER BY u`, `... GROUP BY 1
ORDER BY 1`) fails to plan with `VAR_REF_NOT_FOUND` on the column inside the expression, as the same query written in
PartiQL does; the `ORDER BY` key is resolved against the input of the grouping, not its output. Grouping and ordering
by a column works.

Known differences that are not refused: the aggregates `AVG`, `COUNT`, `MAX`, `MIN`, and `SUM` are translated directly,
and `AVG` of an integer, which Redshift truncates, is not yet rewritten; `NULLIF`, `DECODE`, `GREATEST`, and `LEAST`
compare `CHAR(n)` values with their padding, which Redshift disregards, and compare values of different types as
PartiQL does, where Redshift converts one to the type of the other: `DECODE(caldate, '2008-06-01', ...)` from Redshift's
own example converts the string to a `DATE` in Redshift and is never equal in PartiQL (refusing it needs the column's
type, which the planner has and this front end does not); `NVL2`, `DECODE`, `GREATEST`, and `LEAST` return a value of
either branch's type where Redshift converts to a common type (`NVL2(x, '2345', 1234)` is a `VARCHAR` in Redshift,
`GREATEST(ts, DATE '2020-01-01')` a `TIMESTAMP`); `UPPER`, `LOWER`, `CONCAT`, and `||` take a value that is not a
character string in Redshift, which converts it to `VARCHAR`, and the planner reports a type mismatch in PartiQL (the
numeric literal operand of `||` and `CONCAT` is the one conversion the front end writes, since it needs no type); `||`
and `CONCAT` of a `CHAR(n)` value keep its padding, which Redshift drops when it converts the operand to `VARCHAR`; `&`
of a `DECIMAL` or floating-point column is an error in Redshift, where PartiQL casts the operand to `BIGINT`, which
rounds (`2.5` to `2`, half to even, and other engines round their own way); `POWER` of a string column, which Redshift
rejects, casts the string to `DOUBLE PRECISION` at run time; `POWER` of a negative base with a fractional exponent, of 0
with a negative exponent, or past the range of `DOUBLE PRECISION` is an error in Redshift, where a target may return
`NaN` or `Infinity`; an unnamed select item is
named `_n` by the planner where Redshift names it after the function as written (`coalesce`, `case`, `greatest`,
`upper`, `power`) and an operator's `?column?`, so
`SELECT NVL(b, 0) FROM t ORDER BY coalesce` does not resolve; `ILIKE` folds the case of every letter through
`LOWER`, where Redshift folds only single-byte characters; a `CHAR` or `VARCHAR` length is a number of bytes in Redshift
and of characters in PartiQL, and the number is kept; a `LIKE` pattern that is not a literal keeps Redshift's escape
character, and PartiQL rejects at run time an escape before a character other than `%`, `_`, or the escape itself, which
Redshift takes literally.

## Tests

- `src/test/resources/grammar/accept/*.sql` and `reject/*.sql`: the grammar fixtures, statements that must parse and
  statements that must fail with the expected `line:column`, grouped by reason. `RedshiftParseTreeTest` checks the
  shape of the parse tree where the grammar has to choose.
- `src/test/resources/redshift-frontend/inputs/<group>/*.sql` and `outputs/<group>/*.sql`: the conformance suite, one
  Redshift input and one expected result per case: the input is converted, planned against the Scribe test catalogs
  (`src/test/resources/catalogs` of the root project, with the scalar function `pow` over two `DOUBLE PRECISION`
  arguments added by `RedshiftTestSession`), and compiled with the PartiQL target. An expected result is
  PartiQL text, compared up to whitespace, the front end's problem code with a message fragment
  (`[UNSUPPORTED_OPERATION{message="function DATEADD"}];`), or the planner's (`[PLANNER{message="VAR_REF_NOT_FOUND"}];`).
  `RedshiftTranspilerSuite` runs them, parses and plans every valid output again as a check, parses every input with
  the grammar, and checks that `tables` names the tables the AST reads.
- `RedshiftTranspilerTest`: the public contract: problem codes and kinds, positions, notes, determinism, the nesting
  limit, and the AST planned and compiled by `RedshiftTarget`. `RedshiftParserClassPathTest`: `RedshiftGrammar` by
  parser class and from the class path, another parser refused, and a missing parser reported at construction, through
  a class loader that hides it.

```
./gradlew :partiql-scribe-redshift-frontend:test
```

The build needs JDK 17.
